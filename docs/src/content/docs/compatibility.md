The current verified target is GPUI Kit and its exact `gpui-pre` snapshot.
Longbridge publishes the `gpui-pre-*` family as snapshots of Zed GPUI; its version
numbers are independent of the official `gpui` crate.

The macro and core crates have no GPUI runtime dependency. The demo names
`gpui-kit` as `gpui` to preserve paths used by RSX expansions and GPUI derives.

<!-- gpui-rsx:compat:start -->
### Verified Compatibility

| GPUI-RSX | GPUI Kit | GPUI snapshot | Component |
| --- | --- | --- | --- |
| `0.12.0` | `0.9.0` | `gpui-pre@0.3.11` | `gpui-component@0.9.0` |

This matrix comes from demo/Cargo.lock. Kit supplies GPUI, components and assets; the Cargo alias below preserves the gpui:: path used by RSX expansions. Commit the application lockfile.

```toml
[dependencies]
gpui = { package = "gpui-kit", version = "=0.9.0" }
gpui-rsx = "0.12.0"
```

## Verification Scope

| Target | Validation | Scope |
| --- | --- | --- |
| Kit snapshot pinned in the matrix | Generated API contract, demo builds, tests and doctests in Linux/macOS CI | Primary target for the mapped GPUI methods and documented Kit integration |
| Renamed Kit dependency | Separate fixture in the demo CI job, without a `gpui` crate alias | Configured GPUI paths, components, IDs, fragments, inline dynamic classes and shared runtimes |
| Official `gpui = "=0.2.2"` | Separate macOS fixture sharing regression cases | Key, component-default, fragment, event, identity and state-update cases; not the full generated API contract |
| Other versions, sources or backends | Not covered by this matrix | Validate the application's dependency graph, generated code and behavior before adopting |

The macro having no GPUI runtime dependency does not establish compatibility with every
GPUI version. Keep the default `gpui` dependency name or configure `gpui-path`, import the
required traits, and use the appropriate component constructors. The `doctor` and
`check-gpui` commands inspect the resolved dependency graph; a successful result does not
type-check RSX or replace application tests.

Use the pinned combination to establish a baseline before changing one dependency at a
time. For an unverified combination, include the manifest, lockfile, smallest failing RSX
and compiler output when reporting a compatibility problem.

## Existing dependency aliases

Prefer the `gpui = { package = "gpui-kit", ... }` form above. If an application
already names that dependency `engine`, expose the expected crate name at its root:

```toml
[dependencies]
engine = { package = "gpui-kit", version = "=0.9.0" }
```

```rust
extern crate engine as gpui;
```

Each binary, example or integration-test target using RSX needs that alias in its own
crate root when using the default configuration. Alternatively, set an absolute GPUI path
in the project's `rsx.toml`:

```toml
[options]
gpui-path = "::engine"
```

This option covers generated references in markup, components, automatic IDs, dynamic
keys, `rsx_listener!`, `rsx_update!` and `rsx_runtime!()`. `crate::ui` also works for a
crate-root re-export. Paths cannot contain generic arguments or start with `self` or
`super`; every target using a crate-local re-export must provide that re-export.
The explicit `rsx_runtime!(::other_engine)` argument overrides this option.

With a configured path, `#[component]` functions implement `IntoElement` through
`ViewElement`, so the path must point at a GPUI that provides it. GPUI 0.2.x (which uses
`Component`) supports these generated function components only with the default `gpui` name.

Existing `rsx.toml` files are tracked by macro expansions. To also detect a file first
created after compilation, add this to the consuming package's `build.rs` (or merge the
directive into its existing build script):

```rust
fn main() {
    println!("cargo:rerun-if-changed=rsx.toml");
}
```

The demo includes this build script. It tracks config creation, edits, deletion and
recreation without touching Rust source. Cargo rebuilds while the tracked file is absent;
keep an empty `rsx.toml` to disable configuration without repeated rebuilds. Without this
build integration, creating the config requires a Rust source edit to trigger expansion.

User expressions, explicit prop types and GPUI's own derive macros retain their own
imports. For example, an upstream `#[derive(engine::IntoElement)]` may still generate
`gpui::` references and require a user alias. Function components generated by
`#[component]` use the configured path directly. The fixture below verifies operation
without a `gpui` alias:

```bash
cargo +1.98.1 test --manifest-path tests/fixtures/gpui-renamed/Cargo.toml --target-dir demo/target
```

The root MSRV and demo toolchain are managed separately. Working on the macro does
not require GPUI platform dependencies.

## Published GPUI 0.2.2 Regression Checks

A separate macOS fixture compiles and runs dynamic string keys, numeric component
defaults, mixed root fragments, listener signatures, identity and explicit state updates
against `gpui = "=0.2.2"`. It uses `font-kit`, `runtime_shaders`, `test-support` and
GPUI-RSX's `tailwind-scale`, sharing regression sources with the Kit demo tests:

```bash
cargo test --manifest-path tests/fixtures/gpui-0.2.2/Cargo.toml
```

These checks cover the reported macro behaviors; the full generated GPUI API surface
continues to target the Kit snapshot in the matrix above.

## Share One GPUI Type Identity

Use Kit's exports through `gpui::component`, `gpui::base` and `gpui::platform`.
Call `gpui::init(cx)` before opening windows and use `gpui::open_window(...)` to
mount the root. Load icons with `application().with_assets(gpui::assets::Assets)`.

Applications no longer need direct dependencies on the old Zed Git `gpui`,
`gpui_platform`, or Git component library. Each crate instance owns distinct Rust
types; types from different GPUI instances cannot be interchanged.

```bash
cargo xtask check-gpui
cargo tree --manifest-path demo/Cargo.toml --locked -i gpui-pre
```

`check-gpui` requires one rendering engine, matching platform/macros snapshot
versions, and the same GPUI instance in Kit, base and component. It prints the
verified package versions as JSON for CI.

## Update the Matching Set

Follow Kit's published releases. The compatibility workflow selects the latest
stable, non-yanked Kit on crates.io, updates the exact demo pin, and regenerates
the lockfile, API tables, snapshots, specification and this matrix. Linux and
macOS validate the same patch before a repair PR is created; failures update one
tracking issue.

GPUI Fast is optional. The demo and compatibility matrix cover Kit's default
gpui-pre backend.
